# ADR 001: Вибір Rich Domain Model


## Контекст
При переході на шарову архітектуру постало питання про те, як реалізувати доменні моделі: як Anemic Domain Model (сутності як прості структури даних, логіка в сервісах) чи як Rich Domain Model (сутності, що поєднують дані та логіку/інваріанти).

## Рішення
Обрано підхід **Rich Domain Model**.

## Обґрунтування
1.  **Захист інваріантів**: Rich Domain Model дозволяє інкапсулювати бізнес-правила безпосередньо в сутностях. Це гарантує, що об'єкт ніколи не опиниться в некоректному стані.
2.  **Об'єктно-орієнтований дизайн**: Доменні сутності стають справжніми об'єктами з поведінкою, а не просто контейнерами для даних.
3.  **Зменшення дублювання**: Логіка перевірки полів та бізнес-правил зосереджена в одному місці (в самій моделі або її фабриці), що полегшує підтримку.
4.  **Відповідність вимогам**: Завдання вимагає виділення "ключової поведінки" сутностей та "захисту інваріантів", що є основою Rich Domain Model.

## Наслідки
*   Сутності будуть містити методи для зміни свого стану (наприклад, `add_layer`, `follow_user`).
*   Логіка валідації буде знаходитись у конструкторах або спеціальних фабриках.
*   Application layer (Use Cases) буде відповідати лише за оркестрацію (отримання сутності з репозиторію, виклик методу сутності, збереження результату).
