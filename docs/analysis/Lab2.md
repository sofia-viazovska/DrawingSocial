# Аналіз рефакторингу проекту DrawingSocial (Лабораторна робота №2)

## 1. Зміни в структурі проекту
Порівняно з першою лабораторною роботою, проект було повністю реструктуровано відповідно до принципів **Clean Architecture** та розподілено на 4 чіткі шари:

1.  **Domain Layer** (`app/domain/`):
    *   Містить доменні моделі (`User`, `Drawing`, `Layer`), які не залежать від зовнішніх бібліотек чи БД.
    *   Визначено інтерфейси репозиторіїв (`UserRepository`, `DrawingRepository`).
    *   Реалізовано `DomainFactory` для створення об'єктів з валідацією інваріантів.
    *   Визначено доменні винятки.

2.  **Infrastructure Layer** (`app/infrastructure/`):
    *   Містить реалізацію репозиторіїв за допомогою SQLAlchemy.
    *   Містить ORM-моделі (Entity), які тепер відокремлені від доменних моделей.
    *   Реалізовано мапери (`UserMapper`, `DrawingMapper`) для перетворення даних між шаром БД та Доменом.

3.  **Application Layer** (`app/application/`):
    *   Містить Use Cases (сервіси), які оркеструють роботу доменних моделей та репозиторіїв.
    *   Тут зосереджена логіка взаємодії між різними сутностями.

4.  **Presentation Layer** (`app/presentation/`):
    *   Містить FastAPI роутери (контролери) та Pydantic схеми (DTO).
    *   Відповідає за обробку HTTP запитів та перетворення доменних об'єктів у відповіді API.

## 2. Переваги розділення на шари
*   **Тестованість**: Тепер можна писати справжні Unit-тести для доменної логіки без підняття бази даних чи фреймворку.
*   **Незалежність від технологій**: Доменна логіка не знає про існування SQLAlchemy або FastAPI. Це дозволяє легко змінити ORM або веб-фреймворк у майбутньому.
*   **Чітка відповідальність**: Кожен клас має одну зону відповідальності. Наприклад, `Drawing` відповідає за правила додавання шарів, а `SQLAlchemyDrawingRepository` — за їх збереження.
*   **Захист інваріантів**: Завдяки Rich Domain Model, неможливо створити некоректний об'єкт або привести його до невалідного стану (наприклад, додати порожній шар).

## 3. Недоліки та ускладнення
*   **Більше коду**: Кількість файлів та рядків коду значно зросла через необхідність створення інтерфейсів, маперів та окремих моделей.
*   **Мапінг**: Потреба постійно конвертувати об'єкти з DB-моделей у Domain-моделі і навпаки створює додаткове навантаження (як на розробника, так і на CPU).
*   **Складніша навігація**: Для реалізації однієї фічі тепер потрібно вносити зміни у декілька шарів (Domain -> Infrastructure -> Application -> Presentation).

## 4. Гнучкість зміни БД або фреймворку
Завдяки використанню **Dependency Inversion Principle (DIP)**, зміна БД стала значно простішою. Достатньо реалізувати нові класи репозиторіїв (наприклад, `MongoUserRepository`), які наслідують інтерфейси з Домену, і підставити їх у DI. Жоден рядок коду в `Domain` або `Application` шарах не зміниться.
Аналогічно з фреймворком: Presentation шар можна замінити на gRPC або CLI, не чіпаючи бізнес-логіку.

## 5. Вибір Rich Domain Model
Для цього проекту було обрано **Rich Domain Model**.
**Обґрунтування**:
*   Бізнес-логіка (наприклад, правила лайків, додавання шарів, правила підписки) природно належить самим сутностям.
*   Це дозволяє уникнути "анемічних" об'єктів, які є просто набором геттерів/сеттерів, та запобігає розпорошенню логіки по сервісах.
*   Використання `DomainFactory` гарантує, що всі складні правила валідації перевіряються в момент створення об'єкта.
